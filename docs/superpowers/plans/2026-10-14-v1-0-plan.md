update (PR #60). Read `docs/roadmap.md` ("v1.0: Stable") and this file together. **The remaining work, in order, is section 9.**

  (CI workflow `mutation.yml`, `workflow_dispatch`; the badge is on the README).

## 1. How this project works (read before touching anything)

- **Branch -> PR -> `ci-ok` green -> merge (merge commit).** `main` is protected: never push to it. Use `gh` for PRs and merges (retry on the transient TLS error).
  Delete the branch after the merge (local and remote): the owner wants only `main` to remain.
- **Tags and releases only when the owner says so.** Until then everything goes under `## [Unreleased]` in `CHANGELOG.md`. A release = version the CHANGELOG
  section (`## [x.y.z] - date`, compare links at the bottom), merge, `git tag -a vx.y.z`, push the tag, `gh release create vx.y.z --notes-file ...`.
- **Every change updates the docs in the same PR:** README, CHANGELOG, UPGRADE.md (when something must be done), the demo README, and the relevant `docs/*.md`.
- **Verification before saying "done":** the whole PHPUnit suite against PostgreSQL, `vendor/bin/phpstan analyse --memory-limit=1G`, `vendor/bin/php-cs-fixer fix --dry-run`.
  Integration tests need `FUZZPHONY_TEST_DSN` (e.g. `pgsql:host=127.0.0.1;port=55432;dbname=fuzzphony_test;user=fuzzphony;password=fuzzphony`; the database name must
  contain "test"); without it they are SKIPPED, which looks green. A throwaway PostgreSQL: `docker run -d --name fz-test-pg -e POSTGRES_DB=fuzzphony_test -e POSTGRES_USER=fuzzphony -e POSTGRES_PASSWORD=fuzzphony -p 127.0.0.1:55432:5432 postgres:17`.
- **Demo changes are verified on a real, fresh Docker stack,** not only with a local `php -S` (which runs as the DB owner and hid two bugs in 0.9):
  `cd demo && BUILDX_BAKE_ENTITLEMENTS_FS=0 DEMO_PORT=8010 DEMO_DB_PORT=55433 docker compose -p fzv up -d --build`, wait for `[init] done`, run
  `demo/tools/flows.mjs` and `shots.mjs` in the Playwright image against `http://host.docker.internal:8010` (see the top of those files), then `docker compose -p fzv down -v`.
- **Windows Git Bash quirks:** heredocs with backslashes or mixed quotes break (use the Write/Edit tools or a script file); never `rm -rf` with globs; `MSYS_NO_PATHCONV=1` for docker paths.
- The owner reads Hungarian; code, docs and commit messages are English. End commit messages with the `Co-Authored-By` line your session requires.
- Mutation tests: `infection.json5` / `infection-dashboard.json5`; the full run is the CI workflow `mutation.yml` (~20 minutes). New code should keep the score at or above ~97%.

## 2. Decisions

1. **Documentation: DECIDED (2026-10-14): the docs stay on GitHub** (`docs/*.md`, rendered by GitHub). No static-site generator, no GitHub Pages, no extra build. The work is a better structure, a docs index,
   the new guide and recipes, and a link check in CI (phase 4).
2. **Packages: DECIDED (2026-10-14): ONE Composer package, `fuzzphony/fuzzphony`.** No split packages. Phase 5 removes the split leftovers.
3. **How tight the public API is at 1.0: DECIDED (2026-10-20): shrink it first.** More classes move to `@internal` (the stable surface stays small) in phase 2, released as 0.10.0 before the RC; the owner gets the class-by-class list to confirm BEFORE 0.10.0 is built (step 6 of section 9).

## 4. Phase 2: the public API surface (needs decision 3, still open)

Goal: after 1.0 only the documented surface is promised. Steps:

1. Dump the surface: every class in `tests/Unit/PublicApiTest.php::PUBLIC` with its public methods and constructor signatures (a script or `phpstan`/reflection; write the result to a scratch file).
2. For each class decide: stable public API, or `@internal`. Candidates to look at first: classes whose constructors grew in almost every minor (`SearchGate`, `SearchQuery`, `PostgresEngine`, `Fuzzphony`,
   `FuzzphonySearchFilter`, `SearchComponent`); value objects that should be `final readonly`; interfaces meant to be implemented by users (`Engine`, `Connection`, `SearchGuard`, `ActorResolver`,
   `SearchLog`, `QueryRedactor`, `MetricsCollector`) versus interfaces only the library implements (these can be `@internal`).
3. Constructor growth: from 1.0 on, adding a parameter to a public constructor must be optional and last (named arguments). Decide for each public class whether its construction goes through a builder or a
   named-argument factory so that this stays true.
4. The wider contract (decide and write down): configuration keys (`fuzzphony.*`), YAML index keys, attribute parameters, console command names/options and exit codes, metric names and labels, the `fuzzphony_*`
   table and column names and the layout version (`fuzzphony_meta`), the shape of `explain()` output (probably NOT stable), the rank score values (NOT stable, only the order), the SQL (NOT stable).
5. Breaking changes found in 1-4 go into ONE release (0.10.0) with a complete `UPGRADE.md` section ("From 0.9 to 0.10"), so that 1.0 itself is not a surprise.
6. Update `tests/Unit/PublicApiTest.php`, `docs/architecture.md` (the public API list), and write `docs/api.md` (the stable surface at a glance: classes, what they are for, links).

## 5. Phase 3: the backward-compatibility policy (a document + CI)

Write `docs/backward-compatibility.md` (link it from the README, `SECURITY.md` and `docs/roadmap.md`). It must state:

- Semantic Versioning from 1.0; the public API = phase 2's list; `@internal` is not covered; what counts as breaking (removing/renaming a public class, method or config key; adding a required
  constructor parameter or interface method to something users implement; changing a documented behaviour or default; raising a minimum PHP / PostgreSQL / Symfony version in a minor);
  what does NOT count (bug fixes that make the code do what the docs say, internal SQL, rank scores, `explain()` output, performance, new optional features/parameters).
- Deprecations: announced in a minor (`@deprecated` docblock with the version and the replacement, plus `trigger_deprecation()`-style runtime notice via `E_USER_DEPRECATED` where the call can be detected,
  a CHANGELOG entry "Deprecated"), kept for at least one full minor release, removed only in the next major.
- Supported versions: PHP (8.4+, the ones CI tests), PostgreSQL (15-18), Symfony (the versions the composer constraint allows == the CI list == the README badge), and the rule that a version leaves
  the constraint and CI together in a minor release with a CHANGELOG note. DBAL / ORM / API Platform / UX Live Component ranges.
- Database layout: the sidecar layout version, how it is upgraded (`fuzzphony:schema --apply`, reindex when needed), and the promise that a minor release never requires a reindex without saying so in UPGRADE.md.
- Security fixes: which versions get them (the latest minor of the current major, and say whether the previous minor too); update the table in `SECURITY.md` for 1.x when 1.0 ships.
- CI enforcement: add `roave/backward-compatibility-check` (or equivalent) as a non-blocking job on pull requests that compares the public API against the latest tag, and make it blocking after 1.0.

## 6. Phase 4: the documentation (stays on GitHub)

Content and structure, no site generator:

1. A docs index `docs/README.md` (GitHub renders it when you open the folder) with the reading order: Getting started -> Concepts (index, fields, ranking, typo tolerance, synonyms, the sidecar, sync modes) ->
   Guides -> Reference -> Operations. Link it from the README ("Documentation") and keep the README short.
2. **"Migrating from `LIKE`"** (`docs/migrating-from-like.md`, the roadmap's headline guide): why `LIKE '%x%'` and `ILIKE` fall over (no ranking, no typos, no accents/stemming, sequential scans: use the numbers of
   `docs/benchmarks.md` and the demo's Speed view); step by step: take the query you have, define the index (wizard: `fuzzphony:wizard`), `schema --apply`, `reindex`, replace `WHERE name ILIKE ...` with
   `$fuzzphony->in(...)->query(...)`, keep your filters with `where()`, map `ORDER BY` to ranking profiles, pagination, tests; a mapping table (LIKE patterns -> Fuzzphony query syntax: phrases, `-exclusion`,
   `prefix*`, `field:value`, OR); what you gain and what changes (results are ranked and fuzzy: how to keep exact matching with `fuzzy_mode: never`); a rollout plan (shadow search, compare with the old results, feature flag).
3. **Recipes** (`docs/recipes/*.md`, each short, complete and tested): admin panel (API Platform filter, typo tolerant list); shop (facets, search-as-you-type with `asYouType()` and `suggest()`, synonyms, ranking by
   popularity/recency, `federated()` over products and categories); multi-tenant SaaS (tenant-scoped index, the actor, guards, per-tenant analytics and rate limits, the log). The code of each recipe lives in the repo
   (an example under `docs/recipes/` that a test loads, or code taken from `tests/`) so that it cannot rot.
4. Reorganise the existing pages (`docs/*.md`, `docs/adr/`, `docs/grafana/`) under the index: group them (Concepts, Guides, Reference, Operations), keep the existing file paths (the README, CHANGELOG, SECURITY.md and
   GitHub links point at them: grep before moving anything) or leave a one-line stub that links to the new place.
5. A link check in CI: a workflow that fails on dead relative links and dead anchors in `*.md` (a small PHP/Node script or an action pinned by SHA); run it on pull requests that touch docs.
6. Screenshots exist (`docs/screenshots.md`, `docs/image/`): add the Analytics and Security pages if wanted.
