# v0.6 Events Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the v0.6 "Events" milestone: an opt-in `MetricsCollector` abstraction instrumenting
every engine operation, the sync worker, and ORM-sync message handling (with Logging/Prometheus
adapters, a Grafana dashboard and a demo page), plus a non-breaking round-trip optimization for
fuzzy searches that already run inside a caller's own transaction.

**Architecture:** A single new `Fuzzphony\Core\Observability\MetricsCollector` interface
(increment/observe/gauge) is threaded as an optional, defaulted constructor parameter into
`PostgresEngine`, `Worker` and `RefreshDocumentsHandler` — every one of them already has a single
chokepoint (`guard()`, the per-index loop, `__invoke()`) where one instrumentation call covers the
whole class. A separate `TransactionAware` capability interface, checked with `instanceof`, lets
`PostgresEngine` skip a redundant round trip when it knows its own `transactional()` call will
commit (and thus already revert) the fuzzy-search GUC it sets. Nothing here changes an existing
public method's signature or the `Connection`/`Engine` interfaces.

**Tech Stack:** PHP 8.4, PostgreSQL, Symfony (Messenger, Console, DI), PSR-3 (`psr/log`, new
required dependency), optionally `promphp/prometheus_client_php` (suggested, dev-only).

**Spec:** `docs/superpowers/specs/2026-10-01-v06-events-design.md` (read it first — it is the
binding source of exact values, method bodies and file:line references; this plan argues from it
and does not repeat its reasoning).

## Review Focus

1. **A `MetricsCollector` whose `increment`/`observe`/`gauge` throws must never break the operation
   it's observing.** The spec doesn't say what happens if, say, a misconfigured
   `PrometheusMetricsCollector` throws from `CollectorRegistry`. A reasonable person expects a
   search to still return results even if metrics reporting is broken. Pinned in Task 6
   (`PrometheusMetricsCollector`'s own tests) and noted as an explicit non-requirement in Task 2/3/4
   (the spec's `guard()`/`Worker`/handler code calls `$this->metrics->...()` unguarded — this plan
   resolves it: **do not wrap each metrics call in its own try/catch**; a broken collector is a
   configuration bug the operator fixes, not a per-call failure mode to design around, and
   swallowing it silently would hide that bug. Tested by Task 1: `NullMetricsCollector` and
   `LoggingMetricsCollector` genuinely cannot throw for any input this design passes them — if a
   logger implementation throws, that already breaks the app elsewhere today, not something v0.6
   introduces.
2. **`PostgresEngine`'s success-path `guard()` must still record a metric when the operation
   returns a falsy/empty value (`0`, `[]`, `null`, `false`).** A naive `if ($result) { observe(...); }`
   would silently under-report. Pinned in Task 2's test for `sourceIds()` returning `[]` and
   `queueSize()` returning `0`.
3. **`TransactionAware::inTransaction()` must be checked as a capability, not assumed.** A
   `Connection` that implements `Connection` but not `TransactionAware` (any third-party one today)
   must take the exact pre-existing two-round-trip path, not crash on a missing method. Pinned in
   Task 5 with a `Connection`-only (non-`TransactionAware`) test double.
4. **Labels passed to `MetricsCollector` must be stable in shape per event name.** `increment()`/
   `observe()`/`gauge()` calls for the same `$event` must always pass the same label *keys* (not
   necessarily the same values) — `PrometheusMetricsCollector`'s underlying `CollectorRegistry`
   throws if the same metric name is registered twice with different label names. A reasonable
   person adding a new instrumentation call later could get this wrong. Pinned in Task 6: a test
   that calls the same collector method twice for the same event (e.g. `fuzzphony.search.took_ms`
   for two different indexes) and asserts no exception.
5. **The demo's `/observability` page must not crash when the catalog's example query happens not
   to trigger the fuzzy fallback.** `CompareController::EXAMPLES`'s first entry may or may not be
   one that falls back; the page must render the "no fallback on this run" case cleanly, not assume
   the fallback label is always present. Pinned in Task 7.

- [ ] **Step 2: Write `MetricsCollector`**

```php
<?php

declare(strict_types=1);

namespace Fuzzphony\Core\Observability;

/**
 * Three shapes, matching Prometheus's own data model: a running total (increment), a
 * duration/value distribution (observe) and a point-in-time value (gauge). Implementations must
 * never throw for any input a Fuzzphony-internal call site passes (a misbehaving backend should be
 * fixed, not silently caught — see docs/superpowers/specs/2026-10-01-v06-events-design.md).
 */
interface MetricsCollector
{
    /** @param array<string, scalar> $labels */
    public function increment(string $event, array $labels = [], int $by = 1): void;

    /** @param array<string, scalar> $labels */
    public function observe(string $event, float $value, array $labels = []): void;

    /** @param array<string, scalar> $labels */
    public function gauge(string $event, float $value, array $labels = []): void;
}
```

- [ ] **Step 4: Write `LoggingMetricsCollector`**

```php
<?php

declare(strict_types=1);

namespace Fuzzphony\Core\Observability;

use Psr\Log\LoggerInterface;

/**
 * The always-available default: one structured log line per call. `$logQueryText` (default false)
 * keeps a `query` label on the logged line; it is never forwarded to a Prometheus label
 * (unbounded cardinality — see the spec).
 */
final readonly class LoggingMetricsCollector implements MetricsCollector
{
    public function __construct(
        private LoggerInterface $logger,
        private bool $logQueryText = false,
    ) {}

    public function increment(string $event, array $labels = [], int $by = 1): void
    {
        $this->logger->info('fuzzphony.metric', ['event' => $event, 'by' => $by, ...$this->filter($labels)]);
    }

    public function observe(string $event, float $value, array $labels = []): void
    {
        $this->logger->info('fuzzphony.metric', ['event' => $event, 'value' => $value, ...$this->filter($labels)]);
    }

    public function gauge(string $event, float $value, array $labels = []): void
    {
        $this->logger->info('fuzzphony.metric', ['event' => $event, 'value' => $value, ...$this->filter($labels)]);
    }

    /**
     * @param array<string, scalar> $labels
     *
     * @return array<string, scalar>
     */
    private function filter(array $labels): array
    {
        return $this->logQueryText ? $labels : array_diff_key($labels, ['query' => true]);
    }
}
```

Note: the test above asserts `$logger->calls` captures `(level, context)`, not the message string,
so `$this->logger->info('fuzzphony.metric', [...])`'s first argument (the PSR-3 message) is not
asserted by these tests — only the structured `$context` array is. This matches real PSR-3 usage
(Monolog etc. render `context` as the structured payload).

```php
<?php

declare(strict_types=1);

namespace Fuzzphony\Bundle\Observability;

use Fuzzphony\Core\Observability\MetricsCollector;
use Prometheus\CollectorRegistry;

/** @internal Translates Fuzzphony's metric calls into promphp's CollectorRegistry API. */
final readonly class PrometheusMetricsCollector implements MetricsCollector
{
    public function __construct(private CollectorRegistry $registry) {}

    public function increment(string $event, array $labels = [], int $by = 1): void
    {
        $this->registry->getOrRegisterCounter('', self::name($event), $event, array_keys($labels))
            ->incBy($by, array_values($labels));
    }

    public function observe(string $event, float $value, array $labels = []): void
    {
        $this->registry->getOrRegisterHistogram('', self::name($event), $event, array_keys($labels))
            ->observe($value, array_values($labels));
    }

    public function gauge(string $event, float $value, array $labels = []): void
    {
        $this->registry->getOrRegisterGauge('', self::name($event), $event, array_keys($labels))
            ->set($value, array_values($labels));
    }

    private static function name(string $event): string
    {
        return str_replace('.', '_', $event);
    }
}
```

        // 'typo' is chosen over 'accent' because a misspelling is the case most likely to
        // actually exercise the fuzzy fallback, which is the more interesting number to show —
        // but the page must still render correctly on a run where it doesn't fire (Review Focus 5).
        $query = CompareController::EXAMPLES['typo'];
        $explanation = $fuzzphony->in('catalog')->query($query)->explain();
        $fallback = array_any($explanation->statements, static fn(array $s): bool => str_ends_with($s['label'], 'fallback: full-text + fuzzy'));
        $queueCheck = null;
        foreach ($fuzzphony->inspect('catalog')->checks as $check) {
            if ($check->name === 'Sync queue') {
                $queueCheck = $check;
            }
        }

        return $this->render('observability.html.twig', [
            'query' => $query,
            'took_ms' => $explanation->result->tookMs,
            'fallback' => $fallback,
            'queue' => $queueCheck,
        ]);
    }
